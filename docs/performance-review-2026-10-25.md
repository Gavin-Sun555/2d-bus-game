# A–E 之后的性能复盘：2026-10-25

本轮只研究，游戏源码、配置、用户存档及根目录应用均不修改。结论：继续深挖普通小车直线跟车的优先级应下降；先试死锁检测的局部候选，再试环岛重复几何，随后评估公交感知与路口轨迹数据复用。暂不需要直接进入全车并行或降低安全检查频率。

后续状态：第 1 项已实施并验证，见 [死锁检测局部查询报告](performance-recovery-2026-10-25.md)。第 2 项也已实施并验证，见 [环岛入口精确几何报告](performance-roundabout-2026-10-25.md)。第 4 项中的受限试验“铰接车 16 次未来姿态检查共用保守候选”已实施并验证，见 [候选收集试验报告](performance-sweep-candidates-2026-10-25.md)，并未替换全局公交感知。其余方案保持研究状态。

## 这次使用的证据

当前代码包含 A、B、C、D 和最终受限 E，以及最新停站修复。新编译验证工具，串行采集两份真实 Update/Draw CPU profile，没有与测试或其他性能实验混跑。原始数据在 `dist/performance-review-2026-10-25/`，摘要见同名 JSON。

环境：本机 Apple M4，darwin/arm64，Metal，1280×720 逻辑画面，4 倍驾驶视野，垂直同步开启，默认多线程窗口循环。验证场景 seed 5，狂暴自动驾驶；公交均为铰接车型，车速范围 30–80 km/h。

| 本轮带 profiler 场景 | 总更新／预热 | 小车数量 | Update P50 / P95 / P99 | Draw FPS / Update TPS |
|---|---:|---|---|---|
| 48 AI 铰接公交＋玩家 | 6000 / 300 | 864→845 | 15.313 / 17.291 / 18.259 ms | 32.73 / 59.60 |
| 8 AI 铰接公交＋玩家 | 3600 / 300 | 始终 864 | 7.692 / 10.495 / 11.332 ms | 59.94 / 59.98 |

最大 Update 分别 36.93 / 22.07 ms；两轮玩家均无损伤，全部公交最终车况 100%。没有 NaN/Inf 失败。

**这些是带 CPU profiler 的定位轮次，不是新一轮优化前后对照。** 最大车队后段小车下降到 845，不是持续 864 满载验证；也不能与 E 的 3600 更新窗口直接计算收益。CPU profile 包含启动与预热，最大／常用场景分别得到 83.33 / 32.62 CPU 秒样本。Draw FPS 是调用数／墙钟时间，不是显示器逐帧呈现。两轮都不足以替代 10–15 分钟热稳态验收，也不是全屏高分辨率 GPU 测试。

此前无 profiler 的 E 对照仍作为当前较可靠的短窗口基准：最大车队约 40 Draw FPS，Update P50 约 15.06 ms、P95 约 17.48 ms；8 AI 场景约 60 Draw FPS。固定模拟基准支持 E 约 1.38%／2.42% 的小幅改善，详见 [E 报告](performance-e-2026-10-25.md)。

常用场景中死锁检测占总样本 4.20%、环岛入口 6.07%；两项分别约占 Game.Update 累计样本的 12.2% 和 17.6%。这个比例仅表示在模拟调用链中的相对重量，不是按帧耗时测出的节省比例；8 AI 和 48 AI 的路况窗口及 runtime 占比不同，不能直接横比百分数判定扩展曲线。

## 方案 1：死锁检测局部化——建议先试

源码 `internal/traffic/recovery.go:ResolveDeadlocks` 仍对每辆停住的小车扫描全地图路口、其他全部停住小车及 AI 公交。`internal/sim/deadlock.go:DeadlockTimeoutAt` 还会反复寻找最近路口，并为搜索途中更近的路口计算整周期。拥堵时停住车辆多，成本随之上升。

做法：只替换候选收集。按真实最大车辆尺寸求保守查询半径，在现有小车空间索引中找附近车辆，保持原数组槽位顺序；世界路口的 130 px 判定也用局部索引。最近信号灯必须做精确最近查询，保留等距时原先的先后关系，不能误用“附近随便一个路口”。周期可按全部时长依赖缓存，不按当前红绿灯相位缓存。

现有交通更新在调用 ResolveDeadlocks 前把 `spatialActive` 关闭，但索引已逐辆同步到最终位置。实现时应明确提供这个阶段可用的只读查询，而不是随意延长所有索引的启用范围；独立调用、车辆数量变化、读档、异常坐标仍需回退。原逻辑移除第一辆达到阈值的车后立即 break，也必须保持。

风险低至中，潜力小至中。整个检测链才占 4.86% 总样本，即使假设减半，也只是约 2.43 个 CPU 样本百分点的量级示例，**不是实测收益或 FPS 预测**。优势是改动集中，不必让等灯车辆跳过检测、不改死锁计时、不增加绿灯唤醒风险。

验证：对照 isJammed、计时器、实际移除槽位与 RNG 后续状态；覆盖等灯、正常排队、公交让行、环岛、读档及自定义信号周期。

## 方案 2：环岛入口的精确几何预计算——建议第二项

`roundaboutEntryObstacleSpeed` 在一次公交障碍扫描中，已经复用本车的入口路径；但每个障碍仍经 `RoundaboutEntrySeparation.Clears` 进入 `RoundaboutEntryCorridor`，对两条候选入口曲线分别取 33 个点寻找最近位置。`RoundaboutEntryPoint` 每次又通过三个曲线位置求切线，含归一化与三角函数。这个成本可能对大量远处、最终不能获得入口豁免的车辆重复发生。

可以精确缓存环岛／入口方向／车宽相关的曲线采样点、切线和段长度，保留当前采样参数及运算顺序；障碍每帧只做真实位置和朝向的分类。准备保守范围证明后，再排除不可能属于此入口的障碍。首次先做静态几何复用，不先删障碍。两个入口车身各 34 个采样的比较还可研究保守分组包围盒，命中后继续原 SAT。

风险中，潜力中，环岛附近最明显。自定义半径、车宽、地图编辑都必须失效；循环车辆、双入口并行、长尾节以及当前姿态偏差不能漏掉。历史已经缓存本车路径，不能把这项描述成“首次增加环岛缓存”。

## 方案 3：路口轨迹的派生数据和比较去重

`junctionQueueSpeed` 9.29% 中，局部候选收集约 2.21% 总样本，轨迹分离检查约 2.30%；路口本来就已经局部化，继续优化应针对剩余查询、排序和重复曲线计算。

`JunctionLeaderGap` 在多个公交／小车规则中重复遍历轨迹，重新求段长度、单位方向和累计距离，累计约 3.01% 总样本。可将这些量与不可变的轨迹版本绑定；对于同一对完全相同的剩余轨迹，复用“轨迹是否分离”的结果。可先只做同一次调用内复用，再评估跨调用。

风险中，潜力小至中。不能只按指针做缓存：Bodies、Remaining、起点、姿态及连接段可能变化，顺序更新中的其他车也会改变状态。优先保存精确派生数据，原判断与车序不变；不能把不同来源的预测距离、余量或时间步强行合并。

## 方案 4：公交感知按用途筛选——较大的下一阶段选择

`internal/traffic/fleet_update.go` 为每辆 AI 公交复制玩家＋全部小车观察列表，再加入其他公交。多个控制器反复遍历它。不能把“复制列表”本身说成 42% 热点：AI 更新累计 42.48% 包含所有控制、几何与物理，直接列表复制远小于这个数字。

建议从一个函数切入，例如 `controlSweptSpeed`：它已有明确的按本车速度、障碍速度、预测时域与尺寸决定的半径，可以先用保守上界做候选筛选，最终仍执行原逐障碍半径和扫掠。保留障碍顺序和精确两节车身；公交顺序更新时，索引必须反映前面公交的新位置。

不要立刻把所有控制器共用列表改成小半径列表。路口已承诺轨迹、环岛优先权、后方快速来车、站湾队列和超车目的地可能依赖更远对象。适合拆成局部物理障碍、轨迹参与者、站点队列、超车远距四类，无法证明范围则保留全量。

风险中至高，潜力中至高，但候选减少不等于同等 CPU 提升，需要新增查询成本一起测量。比继续扩展 E 到公交尾节更容易限定范围，仍建议每次只替换一种消费者。

## 方案 5：精确姿态预测缓存的下一轮诊断

最大真实场景有约 622.9 万次命中、449.5 万次未命中，命中率约 58.1%；常用场景约 34.6%。固定最大车队基准窗口却只有 26.9% 命中。说明收益高度依赖运行阶段，不能用一种场景直接决定缓存大小。

当前是 128 槽直接映射。下一步先区分“输入确实不同”的必然未命中与“相同输入被其他 key 覆盖”的冲突未命中，再考虑小型组相联或按调用源分区；同时计入 Bus 大结构复制、hash 与查找成本。不能单纯增大缓存、量化角度或减少尾节积分子步。本轮只统计现有 hit/miss，没有采集冲突来源，因此暂不能证明更大的缓存有效。

风险中，潜力待测；C 的既有收益较小，优先级低于明确的重复扫描。

## 方案 6：静态画面缓存与提交批次

Game.Draw 已到 6.13% 总样本，DrawWorld 3.84%；按本轮仪表计时，两场 CPU Draw 提交平均约为 1.50 / 1.37 ms。这不含完整 GPU 执行与呈现，不能用该数证明 GPU 无瓶颈。

可对道路、建筑、树木等静态层做有限尺寸分块缓存，复用几何或渲染纹理；信号灯、乘客、车辆、路线高亮和 HUD 动态绘制。先测实际 draw commands，再选择批次优化，避免已有引擎批处理下重复造轮子。[Ebitengine 官方性能建议](https://ebitengine.org/en/documents/performancetips.html)说明连续且兼容的绘制调用可能自动合批，并提供 `ebitenginedebug` 检查实际命令。

风险低至中，模拟行为不变，但要覆盖缩放／旋转、全屏、地图编辑失效、分块接缝、显存上限和遮挡层次。不是把整个大地图预渲染成一张巨图。适合作为独立于交通算法的备选，不必先降低画质或车数。

## 方案 7：发布构建与 M4 调度复核

ARM64、Metal 已经使用，不能重复计作待做优化。PGO 可以用新的代表性数据重新试，但应混合常用／极限车队、城市／环岛及不同运动阶段；单一微基准并不代表实际游戏。[Go 官方 PGO 文档](https://go.dev/doc/pgo)强调代表性 profile 的重要性。之前本项目约 1.2% 的差异有样本交叠，不能保证这轮会更好。

线程唤醒热点可做专门的系统 trace，并在同样窗口重测默认线程、工具已有 single-thread 参数和 GOMAXPROCS 配置。过去 single-thread 长测没有明显收益，因此本轮不建议直接改默认值。GOMAXPROCS 也不是指定 M4 性能核的亲和性开关。不要通过任意改系统优先级或关闭同步来代替测量。

风险较低、潜力未证实，适合算法稳定后的构建实验。与其先追 M4 指令集或 GPU 仿真，不如减少已经看到的重复几何工作。最后仍需同电源／低电量模式条件的 10–15 分钟热稳态、全屏实际分辨率和呈现 P95/P99 验证；本轮没有修改电源、游戏模式或系统调度设置。

## 方案 8、9：确有需要再改变决策组织

**8：非紧急策略错峰。** 只将超车意图、远处车道选择等战略决策降为较低频率，红绿灯、碰撞、跟车、实际物理和紧急制动保持每 tick 执行；前车／信号／路线变化及时唤醒。超车链约 5.89% 总样本，但并非全部都能安全降频。它会改变决策时机，不能要求逐帧状态与旧版完全一致，需换成行为约束及卡点回归，风险高。

**9：只并行不可变纯计算。** 例如把独立几何预计算分批给固定工作线程，主线程按原顺序读结果并验证依赖。绝不直接让 49 辆公交基于同一旧快照同时决策，那会改变原先顺序避让语义。同步、复制和结果失效重算可能抵消收益；M4 有多个核不等于当前模拟能线性加速。潜力较大，风险及验证成本最高，应留在上述局部方案不足之后。

## 分配与 GC 是否应排第一

额外串行跑一次 300 更新固定最大车队内存基准：299,013 B/update、315 allocs/update。它是单次诊断，不是新的前后性能对照。alloc_space 包含启动、字体加载和预热，不能把其中字体 44.6 MB 误当作每帧泄漏。

主要动态分配方向是 AppendPathBodies／carJunctionScratch 及环岛临时列表，适合跟随方案 2、3 做缓冲复用。CPU 样本中 mallocgc 累计约 0.58%、gcDrain 约 0.23%，均不是当前主要热点；这也不排除 GC 对个别尖峰的影响。暂不建议先大改对象池或 GC 参数来追平均 FPS。

## 推荐顺序和采用门槛

1. **先做方案 1**，逐帧比较计时、移除车辆与 RNG 状态；无稳定净收益就撤回该实验。
2. **再做方案 2**，保持同一组几何采样和碰撞结果；优先静态采样预计算，再决定是否需要候选缩减。
3. 重新采样，按剩余热点在 **3（路口派生数据）、4（公交局部感知）、6（静态绘制）** 中择一，不连续叠加未经测量的改动。
4. 5、7 作为小范围诊断；8、9 保留为更大阶段的选择。

每项使用冻结前后构建，至少三组正反顺序固定模拟基准；真实绘制采用相同种子、相同时长、相同车数轨迹，分别检查 8 AI 和 48 AI，并覆盖实际卡点存档、自定义地图与混合车型。安全类优化保持 60 Hz、车身采样、交通规则、车序不变；局部索引必须对照全扫描结果。

60 Hz 的整帧预算为 16.67 ms，当前最大场景 Update P95 仍约 17 ms，平均或 P50 接近预算并不足够。Update P95 先争取到 13–14 ms 是工程目标，不是 FPS 承诺。一个占总 CPU 5% 的函数即使完全消除，也不可能单独带来整局 30% 的稳定提速；多个相关热点的收益更不能直接相加。

本轮结束时检查 458 个 Go 源码与用户存档哈希，确认未改动。研究没有执行优化实现或重新进行完整 release qualification，也没有解除此前的极限性能发布限制。
