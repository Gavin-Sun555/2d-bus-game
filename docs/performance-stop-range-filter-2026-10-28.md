# 站台判断范围筛选与 CPU 复采样（2026-10-28）

保留第二项的局部实现：小车感知公交停靠状态时，先排除远处站台。
基线已包含第一项“路口候选编号有序去重”，下列收益是第二项的增量，
不能与第一项的百分比直接相加。开发仍在 main，本轮未提交或推送 GitHub。

## 最终实现

生产改动仅为 `internal/traffic/car_update.go` 的感知调用点和新增
`internal/traffic/stop_range.go`。原 `BusStop.ContainsBus` 完全未改动。

若能满足原停靠判断，公交前节中心必同时满足站台纵向、横向限制。
因此两方向限值之和可作为任意世界坐标轴距离的保守上界，无须先计算
旋转或尾节。用 `(站台长度 + 宽度)/2 + 8` 构造便宜的方形排除范围；
额外余量覆盖边界舍入。它不决定停靠，只能排除确定不可能的远处站台。

每辆公交在这次同步感知开始时检查一次前节尺寸、朝向及坐标是否适合
范围筛选；每个站台同样检查尺寸／坐标范围。非常规或非有限数据回到
原完整检查，附近站台也继续原两节车身、朝向、纵向及横向检查。
不缓存跨帧停靠结果，不改车身、队列、让行、预测或碰撞处理。

### 撤回的原型

先前曾试在统一 `ContainsBus` 入口加入同样的快速排除。三个普通场景有
收益，但环岛三组没有稳定改善，部分运行还出现长更新与较大变慢；
没有证明所有波动均由代码造成，也没有忽略这些失败结果。该原型已撤回，
原数据、源码、二进制和微基准保留在
`dist/stop-range-filter-2026-10-27/global-entry-prototype/`，不计入最终收益。
最终仅优化小车感知阶段，避免其他靠站调用承担额外筛选成本。

## 两项完成后的 CPU 复采样

最终组合额外采集四场景各 1800 tick CPU／分配 profile，预热排除在外。
按同步执行阶段打互斥标签；百分比占整个测试进程 CPU 样本，剩余为全局
碰撞、世界更新、运行时和采样器工作，不是整机 CPU 利用率。
公交与小车的交互按执行阶段归属，不代表仅计算自身运动。

后续可优先调查路口缓冲容量／生命周期，或公交入口扫掠的保守候选；
不恢复已暂缓的逐段尾节预测、模拟／渲染流水线或屏外铰接简化。
本轮未继续实施新的优化。

## 行为、安全与交付验证

站台移动／尺寸变化和异常几何，与未改动的完整 ContainsBus 对照。
包含大量真正允许停靠的正例，避免只验证远处都返回 false。

曾误将原 NormalizeAngle 无法返回的无限角度加入诊断，已停止该诊断；
最终 oracle 仅对会正常返回的角度运行，仍保留非有限尺寸／位置等回退检查。
