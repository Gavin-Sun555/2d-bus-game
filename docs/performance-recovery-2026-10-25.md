# 死锁检测局部查询：实施与验证

基于最终 E 版本及最新停站修复，本轮仅实施性能复盘的第 1 项。未修改环岛轨迹、公交控制决策、物理频率、检测周期、死锁超时规则或默认车数。原始构建、对照日志及轨迹保存在 `dist/performance-recovery/`。

## 实现范围

- 小车正常更新结束后，复用已逐辆同步到最终位置的空间索引，只用于死锁检测的附近小车候选。候选半径包含本车及当前最大车辆长度，添加保守浮点余量；候选恢复原数组槽位顺序，仍执行原 Distance、速度、方向和堵塞判断。
- 世界路口的“距离小于 130 px”检查使用静态点网格，地图路口列表逐次校验，坐标原地编辑也会重建。130 px 的严格边界仍用原距离函数判断。
- 最近信号灯仍是精确最近搜索，等距时选择原列表更早的路口。缓存仅复用完全相同位置的超时值；每次检测重新读取信号位置及完整周期。信号增删／重排、时长或道路配置导致周期改变时，清除全部槽位的超时缓存，包括暂时不活跃的容量部分。
- 最近查询的缓存未命中时保留原精确全扫描，没有为了局部化而引入近似最近路口。周期预计算不依赖当前相位；绿灯、让行请求和实际堵塞状态没有被缓存或跳帧。
- 独立调用 ResolveDeadlocks 会重新建立当前车辆索引，不能借用此前碰撞／更新留下的索引。只有正常交通更新内部调用才复用刚完成同步的索引。
- 小车数量 ≤64、禁用空间查询、异常尺寸／坐标及异常公开地图配置走原扫描；没有假设普通小车永远只有一种长度。AI 公交和玩家公交的原有堵塞关系判断保持不变。
- 私有运行时缓存不进入存档。即使车辆替换或槽位重排，也只有位置和信号周期完全相同才能复用超时值；没有复用旧车辆的堵塞结果或计时器。
- 每帧仍遍历车辆并检查恢复状态；仍只移除第一辆达到阈值的车，然后立即停止本轮检测。

## 固定模拟性能对照

本机 M4、darwin/arm64。优化前后分别冻结 game.test 构建，顺序为前→后、后→前、前→后，串行测量，不与回归、race 或 profiler 混跑。每次测量 300 更新；使用既有相同种子和预热基准。

| 场景 | 优化前三次 Update | 优化后三次 Update | 中位数变化 |
|---|---|---|---|
| 864 小车＋8 AI 铰接公交＋玩家 | 7.607 / 7.690 / 7.829 ms | 6.797 / 6.850 / 6.934 ms | 7.690→6.850 ms，−10.93% |
| 864 小车＋48 AI 铰接公交＋玩家 | 11.868 / 11.883 / 12.143 ms | 11.613 / 11.299 / 11.402 ms | 11.883→11.402 ms，−4.05% |

每组优化后均快于对应基线。所有测量保持 864 小车、公交车况 100%；常用／最大基准分配分别仍为约 197 KB／112 次和 299 KB／315 次每更新，没有通过增加动态分配换取查询提速。短基准收益不代表长时间实际画面的相同百分比帧率提升。

## 一致性与回归

- 保留修改前完整 ResolveDeadlocks 作为测试中的独立 oracle。随机 32 组 ×12 次调用，覆盖 0／32／65／300／864／1152 车辆、不同朝向／尺寸／速度、玩家铰接车、AI 双层车、让行请求、信号和路口原地编辑、列表重排、活跃人口缩减以及真正的车辆移除；最终全部车辆字段、计时器和移除顺序一致。
- 六张地图 × 两档车流 ×180 更新：索引实际启用，全部车辆状态与关闭本轮优化的全扫描逐帧一致，后续碰撞挤推结果也一致。
- 1000 个随机位置的最近路口超时精确对照；另测等距优先级、严格 130 px 边界、长尺寸候选、人口 100→65→100、信号系统移除和异常输入回退。补测公开信号列表中途异常后修复时的缓存失效。
- 最大车队 1800 更新轨迹与冻结基线逐帧一致，SHA-256：`eb1d70ed97f883bd31438aaa64e1261f060414a8baf9dce1ee6b7e61055b67d7`。
- 完整 `go test ./... -count=1` 通过；定向 recovery race 与额外异常回退 race 结果保存在证据目录。`go vet ./...` 通过。
- 两份此前停站卡点存档各回放 60 秒，通过开门、实际上下客、路线推进、离站、公交位置连续性及车况检查。回放无固定全局随机种子，仅作为服务和安全证据，不把行程长度差异当作优化效果或严格轨迹对照。

## 实际绘制对照

与固定模拟基准分开串行运行，无 profiler；seed 5、Metal、1280×720、4 倍驾驶视野、864 小车＋48 AI 铰接公交＋玩家。每轮 3600 更新，前 300 预热，顺序前→后、后→前。每轮小车始终为 864、玩家无损伤，全部 AI 公交车况 100%。

| 轮次 | Draw FPS | Update P50 / P95 / P99 | 最大 Update |
|---|---:|---|---:|
| render-0-before | 37.553 | 15.185 / 17.557 / 18.237 ms | 31.271 ms |
| render-1-after | 48.476 | 14.358 / 16.712 / 17.358 ms | 32.392 ms |
| render-2-after | 47.735 | 14.374 / 16.723 / 17.411 ms | 33.826 ms |
| render-3-before | 40.020 | 15.082 / 17.428 / 18.051 ms | 28.862 ms |

两轮中位数：Draw **38.79→48.11 FPS**，Update P50 **15.134→14.366 ms（−5.07%）**，P95 **17.493→16.718 ms（−4.43%）**。正反顺序都重复了改善。

Draw 调用频率的约 24% 提高不能等同于 CPU 加速幅度：模拟接近同步／调度预算门槛时，两者会不成比例。该数字不是显示器实际呈现间隔，也没有达到稳定 60 FPS。每轮约一分钟，不是 10–15 分钟热稳态验收，不能直接与此前 6000 更新、后段小车下降的 profile 比较。

常用车队（8 AI 铰接公交＋玩家＋864 小车）另做前后各一轮真实绘制，每轮 1800 更新、300 预热：两版均约 **59.95 Draw FPS**，Update P50 **7.702→6.807 ms**、P95 **10.971→10.088 ms**。这只是单组常用场景复核，不作为独立的稳定收益百分比证明；三组固定基准提供重复测量支持。两轮车况 100%、864 小车保持不变。

## 采纳结果

保留本轮优化。固定模拟基准及正反顺序真实绘制均支持净收益；完整回归、定向 race、最终构建的 1800 帧轨迹对照及旧停站卡点回放通过。异常输入回退又单独进行了 race 检查，`git diff --check` 通过。

已重建根目录原生 ARM64 `2D Bus Simulator.app`，没有启动／终止用户的游戏、改动用户存档或发布版本。用户存档开始／结束 SHA-256 相同。第 2 项环岛几何优化尚未实施；本轮没有解除极限场景稳定 60 FPS 和长期热稳态的验收限制。详细数值见 [JSON](performance-recovery-2026-10-25.json)。
