# 2026-10-29 性能复测与后续选项

当前 main 工作区，包含最近的公交信号优先、两辆任意车型同时靠站、
公交脱困修复和音效/报站功能。本轮只修改英文上下客提示，去掉秒数前的
`~`；其余为测量和建议。没有实施新的性能优化，也未提交或推送 GitHub。

## 结论

当前存档及一般车队的模拟耗时较低，极端车队的尾部耗时仍高。
满载最明确的瓶颈是公交预测与避障；一般车队仍以小车计算为主。
建议先对**出站脱困的多步预测减少重复障碍扫描**，再做**同次决策的
泊位/几何结果复用**，分别验收后重新采样。

## 离线模拟

M4 MacBook Air、16 GB、Go 1.27.1、darwin/arm64，接电（96% → 99%）。
系统未记录温控或性能警告，但没有持续测温或核心频率记录。
使用固定种子 5、预热 300 tick，测量 1800 tick；每场景两次无 CPU
profiler 计时，顺序正向后逆向。另有独立 CPU/分配采样。不在计时窗口
并行编译、跑回归或分析 profile，未关闭用户其他应用。

### CPU 分拆

CPU 标签按互斥调用阶段划分，包含该阶段的管理、感知、预测、避障等
成本，以及可能继承该标签的运行时样本；不是每辆车自身物理积分的占比，
也不是整机 CPU 使用率。共享函数按调用阶段归属。尾部强制 GC 和 profile
文件写入排除在最终 CPU 窗口之外，修正前的初始采样另行保留，不混用。

| 场景 | 小车阶段 CPU | AI 公交阶段 CPU | 玩家阶段 CPU | 小车/AI 公交墙钟 ms/tick |
|---|---:|---:|---:|---:|
| 当前存档 2 | 55.0% | 33.9% | 5.3% | 2.28 / 1.61 |
| 都会 8 AI | 61.6% | 23.4% | 8.7% | 2.65 / 1.10 |
| 都会 48 AI | 30.3% | 59.5% | 3.9% | 3.62 / 6.92 |
| 环岛 48 AI | 44.8% | 46.5% | 3.4% | 4.01 / 4.61 |

重要调用链的累计 CPU（有嵌套，不能相加）：

- 都会最大车队：`Bus.AtPose` **14.03%**、`controlSweptSpeed` **8.72%**、
  `sidecarSweepClear` **5.76%**、`availableStationBerths` **2.79%**。
- 环岛车队：`stationDepartureEscape` **13.51%**、
  `departureEscapePoseClear` **13.02%**、`sidecarSweepClear` **8.66%**。
- 一般 8 AI：`junctionQueueSpeed` **21.92%**、`carFollowingSpeed`
  **9.44%**。这些流程反复使用路口走廊和前后车几何判断。

分配量约为当前存档 16.2、8 AI 15.7、48 AI 26.5、环岛 24.1 KiB/tick。
各 1800 tick 测量中的 GC STW 累计仅约 0.04–0.10 ms，不能单独解释
几十毫秒的慢帧。profile 仍有内存页操作等运行时成本，若研究这部分，
需要进一步按事件定位，不能直接等同于 GC 暂停或建议修改 GC 参数。

最大车队的分配样本中，`AppendPathBodies` 约占 34%，泊位结果数组约
占 7.9%。这些是分配比例，不能解释成同等比例的 CPU 加速空间。

## 原生窗口短测

另运行 120 秒独立窗口：1280×720、4 倍驾驶视野、都会、48 AI 铰接
加玩家铰接、狂暴自动驾驶、VSync 开启。使用生产的图形预热包装器。
前 20 秒排除，20–90 秒无 profiler 主测，最后 30 秒单独采 CPU。
主测全部 8237 个 Update/Draw 采样均记录为前台，实际小车 844–864。
没有启用音效和系统 TTS，因此不覆盖这两项的耗时。

| 指标 | 结果 |
|---|---:|
| Update 平均 / P99 / P99.9 / 最长 | 13.21 / 22.30 / 25.84 / 32.13 ms |
| Draw 提交平均 / P99 / 最长 | 1.40 / 1.67 / 5.47 ms |
| Draw 开始间隔 P99 / P99.9 / 最长 | 32.11 / 58.51 / 65.87 ms |
| Draw 回调平均 FPS / Update TPS | 57.67 / 60.00 |
| 70 秒内 Draw 间隔 >33.334 / >50 ms | 37 / 13 次 |
| 玩家 / 全部 AI 最低车况 | 100% / 100% |

这是窗口短测，**不是 15 分钟全屏验收**。Draw 提交时间不是 GPU 完成
时间，Draw 开始间隔也不是屏幕实际呈现间隔；未细分的后端等待和调度
仍可能影响慢帧。不能说 GPU 完全没有瓶颈，也不能由平均 FPS 宣布稳定
60 FPS。最后 30 秒 profile 中 `Game.Update` 累计约占 83.2%，进一步
支持先研究模拟；该晚期窗口的车流状态不同，不与前述阶段占比直接比较。

## 可选优化及顺序

以下为待试验方案，CPU 占比只说明覆盖的热点，**不是已测得的收益**。

1. **出站脱困：一次筛候选，复用静止障碍几何。风险低，优先。**
   `stationForwardEscapeClear` 每个转向选择试算 120 步，而
   `departureEscapePoseClear` 每步仍遍历整份障碍并做距离计算。
   到站和侧旁恢复已有一次性筛选，出站这条路径仍可补齐。用两秒内的
   保守可达范围先筛一次，保留原顺序和密集/异常状态的全量回退；静止
   障碍的两节 OBB 也可在这一次试算中复用。保留全部预测步数、身体尺寸、
   余量、重试频率和通行优先级。环岛场景覆盖约 13.5% 的热点，但不可能
   把整个热点成本都消掉，都市/存档的收益也可能很小。

2. **同一次公交决策复用泊位与身体几何。风险低，收益偏小。**
   当前到站、排队、速度和备用停靠分支会反复计算可用泊位，生成短数组。
   在同一 `ComputeControls` 调用内，车辆尚未移动时复用这些结果，使用
   固定两个泊位的存储，减少重复投影和分配。不能跨公交或跨帧复用动态
   占位结果，因为车队仍顺序更新。最大车队泊位函数约占 2.8% CPU，
   不应期待单项带来两位数加速。

3. **继续优化精确铰接预测的内部复用。风险中等。**
   都会最大车队 `AtPose` 约占 14%，现有精确缓存命中率约 45.8%。可进一步
   检查同一姿态下前后节、三角函数和预测结果的重复构造，不降低采样密度，
   不把远处铰接车当直车。需要精确几何/通行回归及轨迹一致性验证；命中率
   并不能证明扩大缓存一定有效。不恢复此前暂缓的逐段积分改算法方案。

4. **小车路口走廊的静态元数据复用。风险低到中等。**
   已有空间索引和候选排序优化继续保留。下一步研究同一已发布走廊的
   静态段方向、边界和投影元数据，减少 `JunctionLeaderGap` 等检查的重复
   计算。动态车位、车速、路权和处理顺序仍逐车更新；走廊变更时必须失效。
   一般车队的路口排队热点约 21.9%，但其中仅一部分可以这样复用。

建议 **1 → 2 → 重新采样**，分别确认实际收益和通行一致性，再决定
3/4。当前没有足够依据优先做渲染流水线、多车并行决策或改变物理精度。
