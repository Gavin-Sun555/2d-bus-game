# 1152 辆小车：热点与优化路线（第二次分析）

后续已实施第 1、2 步，结果见 [实施与测量记录](performance-static-caches-2026-10-22.md)。下文保留实施前分析。

## 本轮实测

Apple M4、macOS。都会地图，1152 辆小车、8 辆公交作为观察对象；每次恢复同一个小车帧，避免车辆离开地图导致结果虚假改善。此基准只测小车管理器的 Update，不含 AI 公交自身驾驶、全局碰撞、绘制等完整游戏开销。公交观察对象停留在固定初始状态，不能代替长时间拥堵场景。

命令：

```sh
go test ./internal/traffic -run '^$' -bench '^BenchmarkTrafficFrame/map0/cars1152$' -benchtime=300x -count=1 -cpuprofile /tmp/busgame-1152-current.cpu -o /tmp/busgame-1152-current.test
go tool pprof -top -cum /tmp/busgame-1152-current.test /tmp/busgame-1152-current.cpu
```

当前结果：12.61 ms/次更新、3,441,464 B/次、4,619 次分配/次。若按每秒 60 次更新计算，仅这部分就产生约 206 MB/s 的分配量；这不是实际帧率测量。60 FPS 每帧总预算约 16.67 ms，当前留给公交、全局碰撞和渲染的余量很小。

CPU 采样累计占比：信号限速约 23%、路口队列约 21%、发布路口行驶走廊约 14%、附近车辆查询约 9%。道路宽度、停止线与转弯几何查询及三角函数反复出现在这些调用链中。这些是嵌套调用的累计时间，不能相加。采样含运行时和初始化，比例是热点定位依据，不是完整游戏各模块的精确分账。

结论：还有明显优化方向。简单的速度/位置积分不是当前主要热点；重复规则查询、几何计算、感知和临时对象更值得优先处理。本轮只修复公交左转等待并完成性能分析，没有实施下列结构性优化，也不宣称已解决 1152 辆场景的流畅度。

## 建议顺序

| 顺序 | 改动 | 收益来源 | 风险与验证 |
| --- | --- | --- | --- |
| 1 | 按地图与车道宽度缓存路口几何、各方向停止线；用空间索引只查询附近路口 | 不让每辆车的多个规则反复扫描道路与所有路口、重复计算同一几何 | 相对低风险；编辑地图、改变车道宽度、读档时重建，保持当前结果逐帧一致 |
| 2 | 缓存转弯走廊/车身采样，复用感知缓冲和临时切片 | 避免每帧、每对车辆重复生成同一组路径车身，减少垃圾回收 | 中等风险；车身当前位置仍需更新，路线变更、变道、掉头时失效，不能保留过期占路状态 |
| 3 | 道路/车道有序车辆索引，快速找前后车；路口单独处理冲突 | 从“扫描一定半径内很多车”改为“先定位相关车道和局部冲突对象” | 中等风险；完整覆盖压线、跨车道、站湾出站和对向车；保持先后优先级 |
| 4 | 分开物理与 AI 决策频率，按风险调度并错开帧 | 车辆运动、近距离避碰和信号安全继续每帧执行，远处畅通车辆少做超车评分/远期规划 | 较高风险；例如 60 Hz 物理、10–20 Hz 非紧急决策是待验证方案，不是可直接启用的安全参数。接近路口、公交、车队或障碍立刻恢复高频 |
| 5 | 快照读取 + 分批并行感知/决策，统一提交与碰撞 | 利用多核分担纯计算 | 较高风险；当前后车会读取本帧前车更新结果，直接为每辆车启动 goroutine 会改变让行与碰撞顺序。须先定义快照、稳定优先级与提交顺序 |

堵在红灯队列里的车辆也可以进入等待状态，由信号切换、前车移动或附近车辆进入唤醒；保留廉价的每帧安全检查。不能只因在屏幕外就停掉车辆：这会改变交通到达时间、堵车与公交运营统计。可把事件驱动等待作为第 4 步的一部分。

优先做第 1、2 步，再判断是否需要第 3、4 步；并行化放在规则和数据访问边界稳定后。不要先降低全局 TPS，否则玩家操控与所有交通都会一起变慢；也不要只减少渲染，因为本次确认的热点在 CPU 仿真查询。

## 验收方式

每一步都保留前后同种子、同车辆/公交数量的对照：固定帧基准与真实游戏长时间运行分开测量。至少覆盖 1152 小车 + 8/16/48 公交、常规/扩大视野、空路/红灯队列/连续路口；记录 Update 的中位数及 P95/P99、分配和 GC、碰撞/闯灯/车辆进度。只报告测出的收益；短时平均低于 16.67 ms 也不能据此保证稳定 60 FPS。
