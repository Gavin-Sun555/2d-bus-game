# 高车流与 M4 MacBook Air 性能优化

本轮优化保留车辆数量、60 Hz 模拟、完整铰接物理与碰撞采样。最大配置仍需要实际渲染长测；不能把一次模拟 Update 低于 16.7 ms 等同于稳定 60 FPS。

## 机器与方法

- 本机 Mac16,12，Apple M4，10 核 CPU（4 个性能核、6 个能效核），16 GiB 内存，macOS 27.0.1。
- Go 1.27.1，darwin/arm64、GOARM64=v8.0，Ebitengine v2.10.4；原生 ARM64 构建。
- 读取电源配置确认电池和接电时低电量模式均已关闭；没有改动系统电源、优先级或线程亲和性设置。`pmset -g therm` 未报告警告，这不等于测得了芯片温度或证明完全没有降频。
- 极限模拟基准：seed 20261024，6 条线各 8 辆 AI 铰接车＋玩家铰接车＋864 辆小车；预热 300 次 Update，测量 300 次，重复 3 次。
- 实际渲染：seed 5，1280×720 逻辑画布、4 倍驾驶视野；分别测试极限 48 辆及常用 8 辆 AI 铰接公交。测试程序自行退出，未操作用户的游戏进程。
- 所有计时实验串行执行，避免与回归测试竞争 CPU。CPU profile 包含预热／启动部分，不能直接把其百分比当作某段实测窗口的百分比。

## 改动

1. 出站、停站旁车与路口扫掠在单次限速扫描中复用相同的两节车身预测。不同采样间距和安全余量分别缓存；缓存不跨控制帧、不进入存档。
2. 通用前方避障只为可能影响其限速的前方车辆／近距离前车做复杂证明。出站后车让行和路口曲线跟车保持独立检查；远车与后车不再重复进行无作用的长距离出站预测。
3. 小车感知的公交列表使用管理器缓冲区。整批小车更新期间，公交位置不变，因此公交是否完整处于站湾内只计算一次；单独调用 StepCar 时仍重新计算，避免保留旧姿态或旧世界的结果。
4. 环岛平行入口检查复用本车入口分类与完整扫掠；另一辆车继续逐一检查。
5. 距离预筛使用平方距离，后续精确碰撞与边界规则不变。
6. 红绿灯候选使用小型栈缓冲和类型化排序，消除每辆车每帧的反射排序分配；超过缓冲容量时仍正常扩展。

这些改动提高 CPU 利用效率，没有修改小车上限、公交容量、加速度、转弯轨迹、交通路权或物理时间步。

## M4 专项研究

- **原生 ARM64 与 Metal**：应用已使用原生 ARM64；Ebitengine 在 Darwin 的默认后端为 Metal。本轮为实测程序增加当前图形后端记录，避免把降低模拟成本归因于更换 GPU 后端。
- **PGO**：用本机真实游戏 Update 的 CPU profile 训练编译器，再交替运行普通／PGO 构建，各 3 次。第二阶段中位数约 14.435→14.261 ms，仅约 1.2%，样本范围存在交叠；没有默认加入 PGO 配置或声称它有稳定的额外收益。参见 [Go 官方 PGO 文档](https://go.dev/doc/pgo)。
- **运行线程数**：第一阶段 PGO 构建用默认 GOMAXPROCS=10 和 GOMAXPROCS=4，各测 3 次，约 16.918→16.665 ms。该设置只是 Go 可同时执行代码的线程数上限，不能把线程绑定到 M4 的 4 个性能核；收益小，因此保留自动调度。
- **游戏模式**：`.app` 已声明游戏类别和 LSSupportsGameMode。Apple 的机制是在支持原生全屏的游戏进入全屏后给予 CPU／GPU 调度优先；若曾为该应用关闭，系统会记住这个选择。本轮没有量化游戏模式开／关的帧率差，也没有改动其开关。参见 [Apple 官方说明](https://support.apple.com/en-us/105118)。
- **更高 GOARM64 等级**：这会改变最低指令集要求，并不是自动利用更多 M4 核心的开关。本轮保留兼容的 v8.0；没有实测数据就不宣称提高等级能加速。参见 [Go 最低硬件要求](https://go.dev/wiki/MinimumRequirements)。

最有效的提升来自削减单核上重复的感知与铰接预测。让所有车辆并行决策会改变当前的顺序路权和避让语义，需要单独设计和验证；本轮没有实施该架构调整。

## 验证与复现

- 最大车队连续 1800 帧状态轨迹：比较玩家／AI 姿态、铰接角、转向、车况、乘客、路线、现金及小车状态，优化前后逐帧哈希一致。最终缓存阶段也全部一致。
- 新增缓存与完整铰接预测的碰撞结果对照，覆盖三种车型、不同铰接角、两套采样间距和多种障碍位置；新增站湾感知刷新及移除公交测试。
- 保留原回归中的绿灯等待、出站、站台排队、环岛、宽路左转、真实存档和碰撞用例。

## 最终结果与发布限制

最终固定模拟基准 3 次结果为 14.131 / 14.438 / 14.455 ms，中位数 **14.438 ms**，每次约 **298987 B / 315 次分配**；相对最初基线约减少 **45.0% 模拟耗时、55.7% 分配字节、84.4% 分配次数**。

| 最终实际渲染场景 | 测量更新次数 | 绘制 FPS | 更新 TPS | Update P50 / P95 | 小车范围 | 玩家／AI 车况 |
|---|---:|---:|---:|---:|---:|---:|
| 864 小车＋8 AI 铰接车，默认同步 | 900 | 59.92 | 59.92 | 8.69 / 9.54 ms | 864 | 全部 100% |
| 48 AI 铰接车，默认同步长测 | 5703 | 14.31 | 53.88 | 18.03 / 20.09 ms | 845–864 | 全部 100% |
| 48 AI 铰接车，单线程窗口循环长测 | 5703 | 14.34 | 53.88 | 18.08 / 20.00 ms | 845–864 | 全部 100% |
| 48 AI 铰接车，关闭同步长测 | 5703 | 18.24 | 54.53 | 17.99 / 19.95 ms | 845–864 | 全部 100% |

默认同步／单线程窗口循环长测带 CPU profiler；关闭同步长测没有 profiler，因此几 FPS 的差距不能全部归因于关闭同步。每段长测约 100 秒模拟时间，6000 次总更新中的前 300 次用于预热。FPS 是引擎 Draw 调用次数／墙钟时间，不是显示器逐帧扫描或 GPU 时间的测量。

另测关闭同步短场景（1200 次更新、前 300 次预热）曾达到 60.56 FPS／58.99 TPS，但长测只有 18.24 FPS，不能将短时的 60 FPS 当成稳定结果。依据 [Ebitengine API 文档](https://pkg.go.dev/github.com/hajimehoshi/ebiten/v2#RunGameOptions)，单线程窗口循环只改变引擎的窗口／图形线程安排，不会自动并行车辆；本项目当前没有后台图形调用，试验可安全进行，但实测没有明显收益。关闭同步可能增加耗电，且本轮不能解决长期满载瓶颈；这些实验均只保留在验证工具的可选参数中，没有改变游戏默认运行模式。

**结论：常用的 8 辆 AI 铰接车负载接近 60 FPS；48 辆极限负载仍不满足流畅发布目标，发布保持 HOLD。** 当前瓶颈仍主要在 CPU 的道路／路口检查、交通队列和铰接预测，不能依靠 M4 编译开关或 GPU 后端切换解决。

后续值得研究的是按路口组织候选车辆与复用准确的局部冲突结果；必须保持顺序路权，继续通过完整状态对照和安全长测。更大范围的并行决策／降低物理频率属于独立架构变更，本轮未实施。
