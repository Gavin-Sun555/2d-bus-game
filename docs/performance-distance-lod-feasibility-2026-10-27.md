# 屏外简化模拟的可行性（2026-10-27）

本轮为可行性分析，未实施距离降级。依据当前 main 工作区源码与刚完成的
CPU 拆分采样，额外调用链／源码行级输出保留在
`dist/distant-lod-feasibility-2026-10-27/`。

## 判断

屏外小车禁止**发起新的可选超车**可行，改动范围较小，但收益有限。
远处铰接车改成直的长车不能同时保持相同的避障／通行语义：真实尾节
几何既参与碰撞，也参与站台、车道占用和驾驶预测。看不到不代表不会
影响交通。两项应独立试验，不捆绑落地。

## 性能空间

以下均指整个模拟进程的 CPU 耗时，不是 FPS、GPU 或整机利用率。
没有实际 LOD A/B；比例为既有 profile 的直接成本上限与条件估算。

| 场景 | 小车超车 prepareCarPassing 累计 CPU | 尾节 advanceTrailer 累计 CPU |
|---|---:|---:|
| 当前存档 16 AI / 793 小车 | 2.80% | 约 3.36% |
| 8 AI 铰接 / 864 小车 | 3.55% | 5.80% |
| 48 AI 铰接 / 864 小车 | 1.09% | 10.05% |
| 环岛 48 AI 铰接 / 720 小车 | 1.11% | 3.60% |

尾节一列不是“每辆实际公交每帧更新”的成本。最大车队尾节积分样本共
1.85 CPU 秒，其中 AtPose 预测调用 1.84 秒，Bus.Update 实际更新仅
0.01 秒（全进程约 0.054%）。其他三个短窗口没有采到实际更新分支，
不能解释为实际开销为零；10 ms 采样粒度不适合精确测量这么小的分支。

- 小车：即使关闭所有区域的超车调用，直接可省也只有约 1.1%～3.6%。
  若 **80% 的超车 CPU 成本**在可降级区域，理想直接节省约
  0.9%～2.8%，还未扣除距离判断和收尾逻辑。80% 为示例，不是已测比例；
  不能以屏外车辆数量占比替代屏外 CPU 成本占比。
- 铰接车：只停掉真实尾节更新而继续原安全预测，净收益可能很小。
  若连远处的尾节预测也取消，最大车队的激进假设是 80% × 10.05%
  约 8% 直接 CPU 空间。但这不能兑现为保证收益：必须恢复的精确检测、
  代理几何、区域管理和状态恢复都有成本，控制决策改变也会改变车流负载。
  目前没有数据支持给出可靠的净加速百分比，更不支持承诺几十个百分点。
- 不应将 AtPose（最大车队 11.20%）与 advanceTrailer（10.05%）相加，
  它们嵌套。若总 Update 耗时少 8%，也不等于 FPS 必增 8%。

## 小车方案的边界与风险

只允许在远区跳过新的可选超车决策。必须保留：

- 已开始的超车、回原车道和当前变道的安全收尾；不能直接把 CanOvertake
  关掉或在 Passing 状态返回，否则会遗留超车状态或无法回位。
- 左右转所需的选道、路口信号、环岛让行、跟车、公交优先和碰撞保护。
- 一套进入／离开远区的不同阈值，避免边界反复启停。可见范围按实际缩放、
  全屏比例和镜头位置计算，外加运动／恢复缓冲；不能只用玩家车的固定半径。
- 远处车流仍与完整公交交通交互。小车不超车会积队，可能造成堵塞回传到
  玩家所在区域，公交站出口／路口也可能因此承压。

该方案可以保持基本安全规则，但不会保留原来的逐帧交通轨迹。
省时后也必须看车辆吞吐和公交等待，不能把更多车停着造成的低 CPU
误认为算法优化成功。

## 铰接车为什么不能简单替换成直车

1. 转弯时前后节朝向不同，尾节存在内轮差；同宽的直长矩形既可能漏掉
   真实尾节占用，也可能覆盖真实车身以外的区域。它不是始终包含真车身
   的保守包围体。
2. 漏占用会产生并线剐蹭、转弯扫到旁车或站台；过度扩大代理则会误判
   相邻车道被挡，重现本项目此前的互让、进站或绿灯不走问题。
3. BodyParts、BodyEnvelope、AtPose 同时被避障、候车、停靠、路口走廊
   和其他车辆的预测读取。保留前车头路线不等于保留驾驶逻辑。
4. 进入近区后强制 TrailerHeading=Heading 会瞬间改变尾节位置和占用，
   可与原本合法处于附近的小车重叠。渐变显示不能修复物理占用突变。
5. 若保留真实尾节状态／历史，再补算以恢复精确状态，会抵销部分收益，
   还可能在镜头移动、缩放或读档时制造一批同时恢复的慢帧。
6. 不应靠切换成普通车型并加倍 Length 实现：前节参考点、轴距、转向、
   站位容量、车型调度和存档都可能受影响。

因此，“仅省掉铰接计算，同时完全相同的通行逻辑且不新增碰撞”不能由
这个直车代理保证。若维持原精确车身用于所有最终安全判断，省下的主要
是部分粗筛工作，而不是整段尾节预测。

## 更保守的替代方向

- 保留所有公交真实尾节积分和必要的精确碰撞；长车代理只作保守粗筛，
  不相交才能提前排除，可能接触时仍使用原两节车身。现有包络与精确姿态
  缓存已经做了一部分，不能重复计作新收益。
- 研究真正直行且尾节已回正的等价预测快路径；转弯、并线、靠站和恢复期
  全量计算。必须验证浮点、尾节状态和完整预测结果，不能仅以“车头看着
  很直”触发。收益需重新统计符合条件的 CPU 样本。
- 如果未来接受“安全但交通轨迹可以不同”，再考虑更广泛的区域模拟等级。
  只在无冲突长直路、非靠站／路口／环岛、无当前变道时降级，保留交互区域
  和提前恢复窗口。条件越严格，可省的热点比例越小；复杂转弯恰是主要热点。

## 建议实验顺序及验收

先单独试“远区小车不发起新超车”，暂不做铰接直车代理。首先统计正常与
4 倍视野下的屏外**超车调用 CPU 权重**，然后用独立开关做交替 A/B。
记录 8/48 车队的 Update P50/P99/P99.9、真实绘制间隔、车辆吞吐、公交
等待、全部车况和内存；同时覆盖已有超车跨区、缩放／镜头跳转、公交进出站、
八车道左转、窄路及环岛、中途保存读档。通行恶化或有新增接触即不保留。

原来两项本地公交修复、用户存档及 GitHub 发布均未改动。
