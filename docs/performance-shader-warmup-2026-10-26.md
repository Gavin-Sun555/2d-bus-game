# 加载阶段曲线着色器/管线预热实验 · 2026-10-26

已保留一个小范围预热：应用启动时先显示加载画面，在 32×32 离屏图上实际绘制一段带抗锯齿的二次 Bézier 曲线，并用一次 `ReadPixels` 提交、等待 GPU 工作，再放行游戏更新。不是仅创建 Go 侧 Shader 对象。地图切换不用重复预热，正常帧不再执行读回。

## 定位到的实际变体

Ebitengine 2.10.4 的 `vector` 曲线模板着色器：

- SourceID：`ll72cqtwjplgbsex5ucq7vz2xm`。
- `ensureStencilBufferBezierShader`，Metal 管线为 `screen=false`、`BlendLighter`（源/目标 RGB 和 Alpha 均为 One，运算 Add）。最终矢量合成是带抗锯齿的 NonZero 填充。
- 首次有效曲线绘制来自驾驶仪表盘的大路口信号灯圆点。诊断的真实提交栈落在 `internal/ui/dashboard.go:89`，前面 83–85 行绘制灯晕、实心圆和圆环。
- Go 侧对象在首帧已经创建；Metal 库仍延迟到这组圆点首次出现时才编译。单纯提前调用创建对象不足以消除尖峰。
- 最早未改动着色器源的定位轮：约 107.8 秒发生库编译 93.69ms、管线创建 7.34ms。该轮未获前台焦点，只用于归因。
- 前台全屏基线：游戏约 87.62 秒才编译目标库，91.64ms；随后目标管线创建 0.17ms。相邻 Draw 开始间隔达到 161.14ms。与之前执行跟踪中 168ms 的同步 Metal 编译事件表现一致。

## 测量设计和边界

M4 MacBook Air、Go 1.27.1、同版本引擎。使用固定 seed 5、都会地图、864 初始小车、48 辆 AI 铰接公交及玩家铰接公交、同一全屏/视角设置，运行 120 秒。原始回调间隔记录不启用 CPU profiler 或 runtime trace。每个更新/绘制回调记录焦点和全屏状态。

指标是 **Draw 回调开始到下一次 Draw 回调开始的墙钟间隔**，包括其间模拟、驱动等待和调度；不是仅 `Game.Draw` 的函数体耗时，也不是 GPU 实际呈现时间。P99/P99.9 使用 nearest-rank，统计游戏开始后 2–120 秒；不将窗口初始化/加载帧混入游戏统计。主比较要求整轮记录持续前台全屏。

为防止先运行基线把驱动磁盘缓存填好、导致预热组白得收益，实验用独立引擎副本和构建 overlay，在生成的 Metal 源末尾附加每个进程不同的无语义注释，制造受控的**源编译缓存未命中**。两组都这样处理，真实几何和着色器功能不变。**没有清空系统缓存、没有重启机器，也没有强制清空管线磁盘缓存**，因此不能将其称为整台机器完全冷启动。管线创建在此实验中可能仍命中驱动缓存。

另以原始生成源、不加注释，交替启动 baseline/warm/baseline/warm，各 3 秒，仅测已有驱动缓存下的启动成本；这组不用于游戏内 P99.9 对照。生产构建使用原始依赖，不包含实验引擎、副本替换、源码注释或诊断输出。

两个预热轮次的目标库编译和同一组管线创建均发生在加载阶段，游戏阶段未再出现任何新的库/管线编译调用。车辆在两个干净预热轮次中均继续运行，玩家和 AI 公交耐久最低均为 100%。

最可靠的结论是：**已将确认过的那次同步编译从游戏中移到了加载阶段，干净对照中对应的约 161ms 尖峰消失。** P99/P99.9 的变化也列出，但不能把全部百分位变化归因于这一个罕见事件；模拟、系统调度和显示服务的轮次波动仍存在。样本是短时实验，不是完整长时间发布资格测试。

预热轮中加载调用总耗时约 465–474ms，**这不是新增的全部开销**：其中也包括正常首帧本就需要的默认着色器、上传和矢量填充工作。应看完整启动差值，而不是把整个调用时间加在原启动时间上。warm-1 的早期工具把就绪标记放在首个世界帧提交之前，其 551.46ms 标记不用于启动比较。

正常源、已有驱动缓存时：

| 首次 Draw 至完整场景就绪 | 第一次 | 第二次 |
|---|---:|---:|
| 基线 | 103.33ms | 84.45ms |

两次预热调用本身为 8.74ms、8.44ms。场景就绪的成对差值约 +0.24ms / +27.74ms，启动调度波动明显；进程到场景的成对时间甚至一快一慢，所以不声称存在精确固定的启动增量。
