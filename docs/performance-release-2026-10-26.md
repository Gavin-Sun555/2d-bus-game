# 0.0.7 性能发布评估（2026-10-26）

> 后续状态：下述通行问题已完成修复及恢复回归，见 [通行修复报告](traffic-progress-2026-10-26.md)。本报告保留修复前的性能数据和当时发布判断。

本轮结论：**被测 M4 MacBook Air 场景的性能达到本轮建议的发布底线；整体发布暂缓，先审查两项通行进度问题。** 8 场原生全屏性能测试均通过性能门槛，但最大车队长测出现约 239 秒停车等待，既有旧湖畔地图长测也再次未达到行驶进度门槛。流畅度通过不能代替通行验收。

本轮只测试、采样和整理方案，没有修改生产 Go 代码、重建正式程序或改写用户存档。详细数据见 [JSON 汇总](performance-release-2026-10-26.json)。原始日志、逐帧数据、profile、测试入口和结束状态位于 `dist/release-performance-2026-10-26/`（被 Git 忽略）。

## 范围与判断标准

- 环境：Apple M4，10 核，16 GiB，macOS 27.0.1（26A434），Go 1.27.1，Ebitengine 2.10.4，Metal，采样边界为接电状态。
- 原生全屏测试共 25 分钟：最大车队 15 分钟、长测后的新建最大车队 2 分钟、常用车队 2 分钟、自定义环岛地图 2 分钟、另外四张地图各 1 分钟。
- 最大车队为 48 辆 AI 加玩家，均使用铰接车；常用车队为 8 辆 AI 加玩家。初始小车设置 864，允许自然减少。被测自动驾驶狂暴巡航为 80 km/h，并非 120 km/h；既有仿真长测另覆盖高速设置。
- 原生全屏、VSync、4 倍驾驶视野，逻辑画布 1280×804，seed 5。资格测试不启用 CPU profiler 或 runtime trace，不修改引擎来制造冷缓存。
- 提议性能底线：平均 TPS ≥59、Draw 回调 FPS ≥58、绘制回调间隔 P99 ≤25 ms、P99.9 ≤50 ms；超过 100 ms 的间隔必须复核。Update P99 以 16.667 ms 为目标。另设停车超过 120 秒必须审查的通行规则。这是本轮测试前记录的建议标准，并非此前已约定的正式发布政策。
- 分析取长测第 30–900 秒，短测第 5 秒至结束，使用窗口内所有样本、nearest-rank 分位数。8 场均未记录到失焦或非全屏回调。这里的绘制间隔是应用 Draw 回调间隔，不能等同于显示器实际呈现时间或 GPU 单帧耗时。

## 原生全屏结果

时间单位为毫秒。小车范围是分析窗口内实际活动数量，不把自然减少的场景称为持续 864 辆压力。

| 最大车队 15 分钟 | 59.70 | 14.86 | 17.96 | 34.41 | 67.48 | 743–864 |
| 长测后新建最大车队 | 59.76 | 14.88 | 17.91 | 32.61 | 33.35 | 843–864 |
| 常用 8 辆 AI，全部铰接 | 60.00 | 7.35 | 17.48 | 18.95 | 19.23 | 846–864 |

主长测分析窗口 870 秒，平均 TPS 59.999，Update 平均 12.04 ms、P99.9 16.30 ms、最大 29.55 ms。Draw 提交回调平均 1.50 ms、P99 2.01 ms。绘制间隔超过 33.334 ms 共 77 次、超过 50 ms 共 20 次（约每分钟 1.38 次），没有超过 100 ms 的间隔。因此可判断总体接近稳定 60 FPS，但仍存在偶发可感知慢帧，不能称为完全无卡顿。

主长测 GC 1383 次，累计 STW 58.98 ms，分配速率约 80.8 MB/s。第 188–864 秒的资源采样中 RSS 为 236.1–245.4 MiB；这不覆盖最初三分钟。系统未报告温控或性能告警，但未测核心温度和频率，不能据此证明完全没有降频。

最大车队后段车流减少且玩家长时间停车，因此不能仅凭后段负载下降判断持续满载表现。长测后重新建立高密度场景，以及海岸、山谷、双城持续 864 辆的小车测试，提供了补充验证。

## 阻止直接发布的通行发现

### 最大车队长测：至少 239.40 秒停车等待

主场景在第 659.70–899.10 秒持续停车，结束时尚未验证恢复。全场玩家移动 54106 px，AI 车队累计移动约 214 万 px；TPS 同时保持接近 60。这属于车辆决策和通行链问题，不能用性能通过来忽略。

已保存 `long-maximum/end-state.json`、`end.png` 和 `long-wait-diagnosis.json/.log`。结束状态中玩家位于约 (-3731.36, 2576.97)，路线 leg 9→8、目标市立第一医院。静态诊断显示玩家被 AI 8 约束，AI 8 被下游公交导致的 `junction_admission=0` 约束，信号本身没有要求停车；移除交通观察对象时这些限制消失。

该证据确认了等待链，**尚不足以断言整条链必然是永久死锁，或某个具体让行阈值就是最终根因**。下一步应回放结束状态，验证下游是否释放、是否存在互相等待，并加恢复进度断言。本轮诊断测试通过仅说明状态加载和诊断成功，不代表卡点已修复。

### 既有旧湖畔狂暴长测：进度门槛重复失败

既有 `TestRelease005TrafficSoak/map3/berserktrue` 在 120 秒仿真后行驶约 6744 px，低于原有 10000 px 门槛。独立进程复测得到同样结果，未调低门槛。结束有效游戏存档已保存为 `legacy-lake-progress-end.json`，日志为 `legacy-progress-recheck.log`。

需要审查这段轨迹是否为异常等待、路线/地图问题或既有门槛与当前场景不符；在未查清前保留失败结果，不据此直接宣称碰撞物理故障。

## 仿真长测与验证范围

既有 opt-in 长测共 21 个叶子场景、42 分钟仿真时间：**20 通过、1 失败**。

| 测试组 | 结果 | 覆盖 |
|---|---|---|
| 高速混合交通 | 3/3 | 三张地图、高速、红灯排队后的有效行驶进度 |
| 普通/狂暴交通 | 11/12 | 六张地图、普通公交；失败为上述旧湖畔狂暴进度 |
| 混合车型 | 6/6 | 六张地图，普通/双层/铰接 AI，铰接玩家，第 60 秒存读档 |

21 场玩家均无健康值损失；8 场原生性能场景与 6 场混合车型长测还检查了全部 AI 的健康值。旧普通/高速测试没有逐 tick 断言全部 AI 健康，不能扩大为所有场景全部车辆零碰撞保证。

本轮没有重新执行完整常规单测和 race 矩阵；上一轮已在相同 Go 源码上通过，此轮源码哈希审计确认未变。此报告属于性能资格及相关通行回归，不能代替完整功能发布验收。

## 当前瓶颈与后续方案

纯仿真测试每场预热 300 tick、测量 1800 tick。两次不启用 CPU profiler 的最大车队测试始终维持 864 辆小车：Update 平均分别 10.209、10.219 ms，P99 分别 11.807、11.833 ms。此测试不含 Draw，绝对时间不能直接与原生全屏相比。

CPU profile 最大车队中，公交更新累计约 47.67%，小车更新约 39.90%；`junctionQueueSpeed` 14.32%、`Bus.AtPose` 11.08%、`separatedBodies` 5.51%。常用车队及自定义环岛的排队逻辑占比分别达到 27.36%、23.53%。这些是嵌套调用，不能相加作为可削减比例。

### 优先 1：复用圆形绘制缓冲，缓存圆周模板（低风险）

这是本轮最明确的新机会。`internal/view/primitives.go` 中 `filledCircle`（第 62 行）和 `strokeCircle`（第 119 行）每次绘制都新建顶点/索引切片，并重算圆周方向。独立 45 秒原生绘制诊断中，两者分别占总分配量 48.04%、12.94%，合计 **60.98%**，累计分配约 2.1 GiB。这是反复分配总量，不是驻留内存，也不是 61% 的帧耗时。

建议按细分步数缓存单位圆方向和索引模板，使用有界可复用顶点缓冲，保持顶点顺序、细分精度、颜色、抗锯齿和绘制顺序。当前已有共享 quad 的实现可作生命周期参考。先交替 A/B 测分配速率、GC、Update/绘制间隔 P99/P99.9，并检查缩放、窗口变化和 AA 像素结果。

预期主要收益是减少分配、GC 频率及分配器开销；由于当前累计 STW 很低，**不能保证慢帧会按分配下降比例改善**。它不改变车辆决策，适合先做独立小实验。

### 优先 2：路口走廊分段几何缓存及保守分块筛选（中风险）

针对排队与车体分离检查的重复几何工作，在现有道路边界缓存和临时数组复用基础上，只缓存尚未缓存的派生几何，或为连续路段建立保守包围范围，减少逐段精确测试。

必须保留原候选车辆次序、精确检测和地图 revision 失效机制；保守筛选不得漏掉铰接车尾节。先统计实际候选/段数削减，再验轨迹、环岛通行、站台恢复和全部车型碰撞回归。目标热点约占 CPU 14–27%，但并非整个热点都能消除，收益尚未实测。

### 优先 3：先测姿态缓存冲突，再试扩大或双路精确缓存（收益待定）

最大车队姿态缓存命中约 55.5%，`AtPose` 累计约占 CPU 11.1%。先区分必然的首次查询、键变化与 direct-mapped 冲突；命中率本身不能证明缓存容量不足。若冲突显著，再尝试扩大或双路缓存，保留完整逐位键及原预测物理。

此方案不涉及此前暂缓的逐段尾节积分或模拟/渲染 goroutine 流水线。验收应包含逐帧轨迹一致、缓存内存上限、实际 CPU 降幅及原生慢帧对照；没有冲突数据前不承诺收益。

## 启动、采样与结论边界

- 本轮第一次独立测试构建的 warmup 回调约 652 ms，随后新建最大车队约 32.7 ms，其他场景约 7.7–9.0 ms。该回调包括首次引擎渲染初始化、提交等待和预热样本，不等于预热新增开销。本轮没有不预热对照和系统级冷缓存清除，不能由此计算冷启动优化幅度。上一轮受控对照另见 `performance-shader-warmup-2026-10-26.md`。
- 长测测试 app 初始未带游戏类别/Game Mode 支持声明，后续短场景补齐与正式包一致的声明。实际 Game Mode 是否开启未独立观测，不能把结果差异归因于 Game Mode。
- 宿主不是完全隔离环境，长测中记录到 macOS 后台服务较高 CPU 活动；未强行结束系统服务。测试证明本机当时环境下的表现，不能扩展成电池、所有机型、所有分辨率或任意持续时长的保证。
- 原生 CPU 诊断存在大量运行时线程同步开销，阶段标签份额不等于 wall time。逻辑热点排序依据纯仿真 profile，绘制内存排序依据独立分配 profile；不据原生总 CPU profile 宣称 GPU 瓶颈。
- 原始 metadata 中继承的 `analysisExcludedFirstGameplaySeconds=2` 与本轮分析口径不同，应以 `analyze.py` 及汇总中的 30/5 秒窗口为准。45 秒独立诊断的 `profileLastSeconds=0` 也是继承字段，实际采样过程与 profile 文件记录 45 秒；资格测试本身不带 profiler。
