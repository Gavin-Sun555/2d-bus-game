# 环岛入口精确几何预计算

本轮实施性能复盘的第 2 项。基线是包含死锁检测局部查询的当前版本，不使用实施第 1 项以前的数据作为对照。证据目录 `dist/performance-roundabout/`。

## 研究与实现

重新采集基线的 48 AI 铰接公交＋玩家、864 小车、3600 更新／300 预热、实际 Update/Draw CPU profile。总墙钟 60.95 秒，CPU 采样 47.12 秒，包含启动和预热。环岛入口检查累计约 8.98% 总 CPU 样本，入口分类 RoundaboutEntryCorridor 约 7.66%，入口分离检查 Clears 约 7.13%。这些是嵌套链，不能相加或直接换算预期帧率收益。

源码确认：公交判断环岛双入口是否可以并行时，对每个障碍都重复计算两条静态候选入口曲线的 33 个采样点和切线。切线又由三个曲线位置计算，包含归一化。即使车辆完全不属于此入口，也先付出了这些曲线生成成本。

本轮只缓存纯曲线几何：

- 每个自动驾驶控制器独立拥有一个有界缓存，按公交／其他车辆与内／外入口分为四个槽位，互不依赖全局可变状态。
- key 包含 RoundaboutJoin 全部 12 个浮点分量的 IEEE 位模式，区分正负零，不对角度／位置取整。半径、入口方向、车道宽度、影响内圈半径的车宽、地图变更只要改变实际曲线，就会重建精确样本；相同曲线可以安全复用。
- 复用原有 33 个位置、切线及惰性计算的方向角。障碍当前位置、朝向、长宽、与曲线的距离和朝向阈值每次仍用原算式判断。
- 原有 34 个扫掠车身、余量、当前姿态偏差、障碍遍历顺序和 SAT 碰撞判断全部保留。没有减少障碍、车身采样或检查频率，没有改变环岛轨迹或通行规则。
- PrepareRoundaboutEntrySeparation 可选接收几何缓存；原有无缓存调用仍保留，作为独立对照。优化仅接入公交环岛入口检查，不扩展到其他预测器。
- 缓存字段私有，不进入 JSON 存档；读档后可冷启动。控制器按值复制时，几何数组也独立复制，诊断不会修改实时控制器的缓存。

## 精确对照与局部基准

4800 次入口分类，覆盖四个方向、斜向、不同路宽／半径／中心、车型、车宽、位置、朝向、重建及交错使用不同几何。其中 3649 次有效入口的所有车身采样逐浮点位一致。另有 28800 次通行判断与原逻辑一致，1028 次确实允许并行；不是仅比较全部拒绝的场景。

补测距离 12 px、朝向点积 .93 附近的分类边界、正负零 key；完整公交环岛入口限速函数的 120 个场景与禁用缓存时逐位一致，包含动态障碍、停车／运动、三种车型及铰接偏角。

同一入口检查 864 个障碍，每组 300 次、重复三次：

| 版本 | 三次耗时 | 中位数 | 每次堆分配 |
|---|---|---:|---:|
| 原逻辑 | 1.794 / 1.815 / 1.813 ms | 1.813 ms | 0 |
| 精确样本复用 | .260 / .263 / .260 ms | .260 ms | 0 |

局部中位耗时约减少 85.6%。这是针对重复入口分类的微基准，不是整局提速承诺。

## 完整模拟基准

本机 M4、原生 ARM64，冻结前后构建；种子及预热沿用原有基准，每次测量 300 更新。顺序为前→后、后→前、前→后，串行运行，无 profiler 或并行回归负载。

| 场景 | 优化前三次 Update | 优化后三次 Update | 中位数变化 |
|---|---|---|---|
| 864 小车＋8 AI 铰接公交＋玩家 | 6.676 / 6.786 / 6.755 ms | 5.189 / 5.116 / 5.204 ms | 6.755→5.189 ms，−23.18% |
| 864 小车＋48 AI 铰接公交＋玩家 | 11.224 / 11.318 / 11.369 ms | 10.083 / 10.190 / 10.341 ms | 11.318→10.190 ms，−9.96% |

每组优化后均快于对应基线。两场景均维持 864 小车及车况 100%。每更新分配仍分别约 197 KB／112 次、299 KB／315 次；缓存使用控制器内的固定数组，未增加稳态每帧分配。不同窗口的环岛活动程度不同，不能把局部微基准的 85.6% 当作整个环岛场景或整局提速。

## 实际 Update/Draw 对照

与基准、回归及 CPU profile 分开串行运行，无 profiler；seed 5，Metal、1280×720、4 倍驾驶视野、垂直同步开启、默认窗口线程配置。48 AI 铰接公交＋玩家＋864 小车，每轮 3600 更新，300 预热，前→后、后→前。

| 轮次 | Draw FPS | Update P50 / P95 / P99 | 最大 Update |
|---|---:|---|---:|
| render-0-before | 48.536 | 14.315 / 16.702 / 17.330 ms | 30.461 ms |
| render-1-after | 56.564 | 13.135 / 15.069 / 15.953 ms | 28.906 ms |
| render-2-after | 56.620 | 13.386 / 15.171 / 15.713 ms | 32.146 ms |
| render-3-before | 49.190 | 14.331 / 16.625 / 17.227 ms | 19.126 ms |

两轮中位数：Draw **48.86→56.59 FPS**；Update P50 **14.323→13.260 ms（−7.42%）**，P95 **16.664→15.120 ms（−9.26%）**。四轮始终维持 864 小车，玩家无损伤，所有公交车况 100%，正反顺序均重复了改善。

8 AI 铰接公交＋玩家＋864 小车另做前后各一轮，1800 更新、300 预热：两版均约 59.95 Draw FPS，Update P50 **6.809→5.614 ms**，P95 **10.219→6.954 ms**。这是单组常用场景复核，不独立推断长期收益百分比，重复性的依据仍是三组固定模拟对照。

Draw FPS 是 Draw 调用数／墙钟时间，不是显示器呈现间隔；改善幅度受同步和调度门槛影响，不能等同于 CPU 提速。每场约一分钟，未完成 10–15 分钟热稳态验收；最大车队仍未稳定达到 60 FPS，Update P95 还需给绘制和调度留余量。

## 重新采样与采纳

同样 3600 更新的优化后 CPU profile 独立采集，墙钟 60.27 秒、44.24 CPU 秒采样，包含启动与预热。环岛入口检查累计 **4.23→1.40 CPU 秒**，占全进程 CPU 样本 **8.98%→3.16%**。保留的障碍检查和碰撞成本仍存在，因此不期待整条调用链获得微基准同等比例的下降。profile 仅用于确认热点减少，不用其帧率推算优化收益。
